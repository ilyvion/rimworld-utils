RimBridgeServer (the in-game GABP bridge) can be driven by an MCP client through **GABS** (`gabs` CLI/MCP server). This is a separate, parallel launch path — it does not replace or touch the VS Code F5 debug configs, and does not run the mod build step (`preLaunchTask`) those configs use, so build the mod yourself first if needed.

- There's no guarantee `brrainz.rimbridgeserver` itself is enabled in the target instance's `ModsConfig.xml`. If the agent intends to do more than just launch and quit the game — anything that requires an actual GABP bridge session — confirm `brrainz.rimbridgeserver` is present and enabled first, the same way as for RimTest Redux described below.
- **Build with `.vscode/build.sh <version>` (e.g. `.vscode/build.sh 1.6`), never a bare `dotnet build`.** `dotnet build` only produces compiler output under `Source/*/bin`; it does not touch the actual RimWorld mod folder the game loads from (`~/.var/app/.../Steam/steamapps/common/RimWorld/Mods/<ModName>` by default, or `$TARGET` from `build_config.sh`). `build.sh` runs `dotnet build` and then wipes and repopulates that mod folder from the build output plus `About/`, `Common/`, `LoadFolders.xml`, and any configured extra files — skip it and GABS will launch the game against stale or missing mod files, silently invalidating any verification.
- **Always build for the latest/current version last before launching. Launching the game with a build for an older version of RimWorld will result in a lot of errors, tests not running and the mod list resetting.**
- The launcher is `gabs-launch.sh`.
- Each mod project needs its own GABS entry (own `gameId`, own `Working Directory`) — GABS config is per-project, though every project can point `Target` at the same shared `gabs-launch.sh`.
- The initial GABP connection sometimes drops once, early during game startup (`games_call_tool` errors with "GABP client connection closed"); `games_status` will show `running-disconnected` — just call `games_connect` again, no need to restart the game.
- **Do not call `games_stop`/`games_kill` while RimWorld is still loading** (defs/mods still initializing) — RimWorld handles a stop signal badly mid-load and can hang or crash instead of exiting cleanly, and `games_stop` will still report "stopped successfully" even when the real process didn't die (verify independently with `pgrep -af RimWorldLinux | grep -v pgrep` if it matters). Wait until it's reached the main menu or a loaded game first. There's no dedicated "wait for main menu" tool — `rimbridge/wait_for_game_loaded`'s readiness targets (`gameData`, `mapData`, `currentMap`, `playable`, `visual`) all require an actual loaded save/game and time out at the main menu with `"blockingReason":"No current game is loaded."`. Instead, poll `rimbridge/get_bridge_status` and look for `state.programState == "Entry"` with the log stream idle (`latestLogSequence` no longer advancing across polls).
- A recurring benign `games_get_attention` item on startup: repeated `Cannot create FMOD::Sound instance for clip ""` errors (empty audio clip path) — safe to acknowledge via `games_ack_attention` without further investigation. A `severity: "fatal"` entry alongside it (e.g. a `NullReferenceException`) during early startup has so far not been blocking either, if the log stream goes on to show a normal successful startup afterward — but treat that judgment call skeptically per session, don't assume it's always safe to ignore.
- **Before launching for a test run, confirm RimTest Redux is present and enabled in the target instance's `ModsConfig.xml`** (e.g. `.savedatafolder/<version>/Config/ModsConfig.xml`), alongside the mod under test itself. Launching with RimTest Redux missing from the active mod list means `[RimTest Redux] TESTING START`/`TESTING END` will never appear (nothing runs the tests), and has been observed to corrupt/reset `ModsConfig.xml` on that launch, losing the previously active mod list. Check the file (or ask the user) before starting the game rather than assuming the last-known mod list is still correct.
- RimWorld truncates `Player.log` itself on startup, so a stale `TESTING END` from a previous run cannot leak into a fresh one — do not manually delete/truncate the log before launching to "be safe"; that only races the game's own truncation.
- Agents should verify a mod's tests actually pass by launching the game this way and watching for RimTest Redux's test-run markers in the log — see [tests.md](tests.md) for how the tests themselves are written, between `[RimTest Redux] TESTING START` and `[RimTest Redux] TESTING END`, then stopping the game once `TESTING END` appears — **unless the response to the user is going to ask them to (re-)verify something in-game themselves, in which case leave the game running instead of stopping it.** Telling the user to go verify in-game after stopping the game the agent just launched forces them to redo the launch and wait for the game to load work the agent already did. Only stop the game if the task is fully done and nothing further needs eyes-on confirmation, or if the user has said not to leave it running.
- **Don't poll for `TESTING END` with `ScheduleWakeup`/sleep loops — they overshoot and waste time.** Instead, since `TESTING END` is a one-shot terminal marker, use a backgrounded shell wait that blocks until it appears and notifies immediately, e.g. (adjust the version path as needed):
    ```
    until grep -q "TESTING END" ".savedatafolder/<version>/Player.log" 2>/dev/null; do sleep 2; done
    ```
    run via the Bash tool with `run_in_background: true` — this is the "tell me when X is ready" case, so a single notification on match beats any GABS log-tool polling loop too. A fully successful run looks like:
    ```
    [RimTest Redux] TESTING START
    [RimTest Redux] SUMMARY
    [RimTest Redux] [✓] ColonyManagerRedux.Tests || Test Suites : 26 ✓ || Tests : 245 ✓
    [RimTest Redux] TESTING END
    ```
    A failing run shows detailed per-test error output in place of clean ✓ counts — read that output rather than just checking for the markers' presence.

### Investigating a UI/layout bug efficiently

- **Don't speculate from a screenshot for long before touching the live game.** Static analysis of GUI layout math (Rects, scrollview content-height caching, one-frame lag between `EventType.Layout`/`Repaint`) is a rabbit hole — RimWorld's IMGUI layout is stateful enough that many plausible-looking theories turn out not to reproduce. If GABS is available and the bug is visual, prefer reproducing it live over reasoning about it from code for more than a couple of minutes.
- **`rimworld/get_ui_layout` responses are large** (every element in the window, recursively) and get expensive fast across many calls. Scope `surfaceId` to the specific window/dialog/float-menu you need (e.g. `window:<id>:<Type>`), not a broad default, and avoid re-fetching the full window layout when only one element's rect or the scrollview's `scroll` block changed.
- **UI element target IDs from `get_ui_layout` go stale the moment ANY window opens/closes** (a float menu appearing, a dialog closing) — even though the ID _looks_ like it should still refer to the same on-screen row. Re-capture layout immediately before every `click_ui_target` call that follows an intervening UI change; reusing an older capture's target ID silently clicks whatever now occupies that coordinate instead of erroring, which can burn several calls before the mistake is visible (e.g. adding a modifier to the wrong task because a stale row index pointed at a different row after the task list re-sorted/re-rendered).
- **Check a tool's schema with `games_tool_detail` before guessing parameter names** (e.g. `rimworld/scroll_ui_target` takes `targetX`/`targetY`, not `offsetX`/`offsetY`) — a failed call plus the follow-up correct one costs more than one detail lookup.
- **Reproduce with the smallest change that can trigger the bug** before building out a full realistic scenario. For a scrollview-bottom-padding bug, the fix was verifiable by adding just enough tasks to overflow the default window height and scrolling to the bottom — there was no need to replicate the exact task set/values from the original screenshot.
- **A rebuild+restart cycle to verify a one-line fix is expensive** (`games_stop` → `games_start` → `games_connect` → `rimworld/load_game` → `wait_for_game_loaded`, then re-driving the UI back to the same test state, since in-memory task list edits aren't persisted unless you explicitly save). Before restarting, consider whether it is truly necessary; if a restart is unavoidable, keep the pre-fix repro steps minimal so replaying them post-fix is cheap.
